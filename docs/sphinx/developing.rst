Development
===========

The developer documentation is kept as Markdown next to the code, because it is
read on GitHub far more often than in a built manual:

* :repofile:`docs/DEVELOPING.md` — repository layout, how the Java and Python
  halves talk over Appose, why ``python/`` is vendored rather than depended on,
  and how to build the jar.
* :repofile:`docs/PUBLISHING.md` — cutting a release, including the browser-only
  route that needs no ``gh`` and no access token.

Building this manual
--------------------

.. code-block:: bash

   pip install -r docs/sphinx/requirements.txt
   make -C docs/sphinx html        # -> docs/sphinx/_build/html/index.html

``make -C docs/sphinx strict`` is the same build with warnings as errors and
nitpick mode on, which is what CI should run.

A docs build needs **neither** the inference stack nor a GPU: ``conf.py`` mocks
torch, CellPose, BaSiCPy and the rest, so only Sphinx itself is installed. That
is deliberate — the modules under ``python/src/neural_imgs/`` are a
byte-identical copy of the research repository's inference subset, so a docs
build must never become a reason to edit one.

Where the docstrings come from
------------------------------

The API pages are generated by ``sphinx.ext.autodoc`` straight from those
modules. Their docstrings are already reStructuredText using Sphinx roles
(``:mod:``, ``:class:``, ``:attr:``, literal blocks, ``#:`` attribute
comments), so there is no second copy of any explanation to keep in step: the
module is the documentation.

The plugin's build id shown in this manual is read out of
``NeuralClassifyPlugin.java`` at build time, for the same reason — so the
manual cannot claim to describe a version that was never shipped.
